# NTAG216 运输 NFC 卡写入规范

## 写入原则

NTAG216 是 NFC Forum Type 2 Tag，提供 **888 字节**可用用户读写区域，带有制造商烧录的 7 字节 UID、原厂真实性签名和 32 位密码访问保护能力。[1] [2] 本系统不把这部分容量用于存储车辆、司机或结算明细，而是将卡片定位为**随车身份凭证**。

> 车牌、司机姓名、司机电话、路线、装卸地点、方量、单价、金额、审批状态和运输票据均不写入卡片。它们由项目范围、车辆台账、路线运价快照与运输票据状态在服务端实时判定。

## 卡内 NDEF JSON 载荷

| 字段 | 含义 | 是否可显示给现场人员 |
|---|---|---|
| `t` | 固定载荷类型 `RC2` | 否 |
| `c` | 系统车辆卡绑定记录 ID | 否 |
| `p` | 项目 ID，用于先行范围校验 | 否 |
| `r` | 写卡修订号，用于补卡/重写识别 | 否 |
| `n` | 随机挑战值，每次写卡重生成 | 否 |
| `s` | 服务端 HMAC 短签名 | 否 |

该 JSON 通常不足 160 字节，远小于 NTAG216 的可用空间；预留容量不用来扩展个人信息或结算数据。

## 写卡与刷卡流程

| 环节 | 发票管理员/系统动作 | 服务端控制 |
|---|---|---|
| 首次发卡 | 读取卡出厂 UID，绑定车辆与司机台账，生成 RC2 NDEF 载荷 | UID 仅保存为不可逆指纹；记录写卡任务、操作人和设备 |
| 装土点刷卡 | 读卡器读取 UID，管理员确认装土点 | 验证项目、卡状态、车辆、地点管理员、趟次状态与幂等键 |
| 卸土点刷卡 | 同一卡完成第二次刷卡 | 锁定路线、里程、方量和有效运价，形成可核验票据 |
| 补卡/换卡 | 旧卡先停用，新卡生成新挑战值与修订号 | 旧 UID 指纹立即拒绝；全程保留挂失/补卡审计 |

NTAG216 的密码保护可阻止未经授权的内存读写；但它不是加密芯片，也不应作为单独的防复制结算依据。[1] 因此系统始终将 **UID 指纹 + 卡状态 + 项目范围 + 现场地点/管理员 + 服务端签名 + 趟次状态** 组合校验。

## 读卡器与写卡器设置

写卡器必须登记项目、设备编号、型号与状态；写卡成功只能由管理员确认并写入审计任务。建议将 NTAG216 用户区的 NDEF 数据设为写保护或通过密码限制改写，但密码只由受控写卡设备或服务端管理，绝不写入前端页面、卡面标签或操作日志。[2]
