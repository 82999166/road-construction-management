# 宝塔 MySQL 迁移操作记录

## 2026-08-25：迁移前隔离与可用性基线

已确认现有正式 MySQL 8.4 实例持续运行。宝塔新增的 MySQL 8.4.10 初始无法启动，原因是其默认数据库端口与现有生产实例发生冲突；未停止、卸载或改写现有生产数据库。

宝塔新增实例现已使用独立端口、独立套接字与独立数据目录成功启动，并收紧为仅允许本机访问。现有生产 MySQL 的服务状态和监听状态均保持正常，两个实例未共享端口或数据目录。

正式 HTTPS 首页已在未登录状态下完成加载，入口页面与前端资源可正常访问。本阶段尚未创建业务库、导入任何数据、切换应用连接或执行生产数据库迁移。

完成备份脚本修正版本的原子发布后，再次通过正式 HTTPS 首页验证前端入口正常加载。该核验仅验证公开入口与静态资源链路；受限后台功能将在完整备份参数配置完成后进行管理员会话下的真实操作验证。

## 后续门槛

在切换前必须完成源库可验证全量备份、目标实例空库与字符集核验、对象数/表结构/关键记录计数比对、应用连接配置的受控切换、核心业务健康检查及源库保留回滚窗口。

完整备份服务首跑曾因模板仍引用旧发布目录结构而在切换工作目录前退出；未读取或导出业务数据。路径修正后又发现低权限备份账户不应依赖应用发布目录的读取权限。备份脚本现改为安装到专用只读运行时目录，修正版本通过发布门禁后将重新安装服务并首跑验证。

受控服务首次真正执行表清单查询时，发现脚本将 MySQL 客户端返回对象错误解构，因而在导出前退出；未生成任何不完整备份文件。该运行时错误已定位，补充回归断言并将重新发布后再执行首跑验证。

后续首跑发现导出进程可能在压缩管道结束前已触发关闭事件。原实现过晚注册关闭监听，Node 在未完成清单写入与锁清理时提前退出。现已在启动导出进程后立即登记关闭事件，再等待压缩完成和进程退出，随后才写入清单；残留锁仅会在确认备份服务未运行时清理。

在宝塔目标实例恢复排查期间，再次通过正式 HTTPS 首页核验现网应用仍可正常加载。该核验仅说明现有生产应用及源库链路未受目标实例操作影响；尚未切换任何应用数据库连接，也未执行生产数据导入。

在后续目标实例凭据恢复排查后，第二次正式 HTTPS 首页核验同样成功。迁移工作已在目标实例凭据恢复未完成处暂停；源 MySQL、正式应用和已验证的完整备份基线仍继续作为唯一生产运行链路。

用户提供的宝塔数据库页面截图经分段核验：页面显示 MySQL 8.4.10 处于运行状态，数据库列表为零条，界面提供“root密码”入口。该状态与“宝塔隔离目标实例尚未导入应用库”一致，不表示现有生产数据库丢失；在受控 root 访问恢复与迁移预检完成前，不在面板手工创建应用数据库或导入数据。

## 2026-08-25：正式迁移完成与迁移后核验

用户明确授权正式迁移后，已按受控流程完成最终源库备份、导入宝塔 MySQL 目标实例、逐表行数与信息架构语义定义校验、应用连接切换及目标库首次完整备份。源库与目标库均核验为 90 张基础表；结构校验使用列、索引、外键、检查约束、引擎及排序规则的语义指纹，避免 MySQL 导出文本格式差异造成误判。

迁移过程中两次失败均由自动回滚保护恢复至源库：首次为文本建表定义格式差异，后续改为语义校验；第二次为低权限备份服务凭据文件归属不正确，现已保持 `0600` 并归属专用备份账户。迁移脚本同时增强为：仅当应用仍连接源库时，才可清理表数为空或与源库一致的未启用目标副本；任何异常均恢复原应用连接并重启服务。

最终核验显示，正式应用服务处于运行状态且已连接宝塔目标实例；宝塔目标库包含 90 张基础表，正式 HTTPS 首页正常加载。完整备份服务最近一次结果成功，定时器已启用并处于运行状态，最新成功清单存在且表数量为 90。原系统安装的 MySQL 仍保留为回滚基线，未删除、未覆盖。

## 2026-08-25：宝塔单库手工备份修复与双重灾备核验

用户在宝塔数据库页面触发单库备份时出现应用账户认证提示。经脱敏诊断，业务应用本身始终可连接宝塔目标实例；问题来自面板中既有数据库记录保留了默认本地实例类型。已先对面板原记录建立受控回滚快照，再将其修正为目标实例的本机连接配置，并复核账户、端口与运行时应用配置一致。该操作仅更新宝塔面板元数据，不修改业务库表、应用连接或业务数据。

后续 MySQL 8.4 导出诊断确认，低权限账户导出业务表本身完整，但默认 `mysqldump` 会读取表空间元数据并要求全局 PROCESS 权限。为遵循最小权限原则，已在宝塔 MySQL 客户端导出配置中启用 `no-tablespaces` 默认项；该修改未重启 MySQL，也未向应用账户授予 PROCESS 权限。按面板真实请求语义复测，宝塔单库手工备份成功。

服务器端完整灾备同步复核：一次性备份服务保持按需运行模式，日定时器处于启用状态，最新成功清单仍为 90 张表。宝塔单库备份用于面板内的便捷操作；服务器端完整灾备继续承担包含校验清单、哈希与保留策略的主要恢复基线。两者并行运行，且不向浏览器暴露数据库凭据、服务器路径或恢复口令。

## 2026-08-25：完整备份隔离恢复演练与数据完整性核验

在隔离恢复演练中，检测到完整备份文件包含原数据库的 `CREATE DATABASE`、`USE` 与 `DROP TABLE` 上下文。首次演练发现导入没有写入预期的临时库后，立即停止后续导入；未执行任何新的删除或恢复操作。随后先触发一次完整备份以冻结当前目标库状态，并对原系统 MySQL 与当前宝塔目标库执行只读核验：两端均为 90 张基础表，表名差异、逐表行数差异和逐表内容校验差异均为零。因此，没有发现此次演练造成的数据丢失或内容变化。

恢复脚本已改为先展开备份、移除原数据库的创建与删除上下文，并且只将 `USE` 语句改写为临时恢复库。脚本在导入前会验证原库上下文已全部消除、临时库上下文已存在；任何失败均通过清理逻辑删除临时恢复库及临时凭据文件。修正后，最新完整备份已成功导入隔离临时库，恢复得到 90 张基础表且结构语义指纹与当前业务库一致；临时恢复库随后自动清理。

演练完成后再次核验：正式应用服务保持运行，服务器端完整备份定时器保持启用，正式 HTTPS 首页正常加载。该演练使用真实备份与真实隔离恢复库，不插入任何模拟业务数据，也不将恢复库暴露给应用或面板用户。
